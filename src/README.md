# Rivermark Chronicles — Open 5e Browser RPG

Single-player, browser-based RPG inspired by classic gold-box games: grid exploration, town hubs, quests, and tactical turn-based combat. Rules and named content are limited to the **5e System Reference Document (SRD)** under **OGL 1.0a** / **CC-BY 4.0**.

## Requirements

- PHP 8.1+ (with PDO MySQL)
- MySQL 8.0+ or MariaDB
- Nginx or Apache with PHP-FPM
- No Composer dependencies

## Play loop (MVP)

This is a **text game**: every scene is prose, everyone in it is a list, and
every way out is a menu item.

1. Open the site → **Create Character** (point buy, standard array, or random).
2. Start in the **Golden Flagon** inn.
3. Talk to Mara, take the cellar job, rest for 5 gp.
4. Out to the **High Street** and the **Market Square**; visit Tobin and the captain.
5. Down to the **Flagon Cellar** — something is eating the stores.
6. Through the **east gate** into the **Quarry Wilds**, and on to the **Goblin Warren**.
7. Fight, loot, finish quests, come back and rest.

Controls: click an exit, a person or an action — or use the keyboard, which is
faster and is the point of a menu-driven game:

| Key | Does |
|---|---|
| **1**–**9** | take that way out |
| **T** | talk to whoever is here |
| **S** | search the place |
| **L** | take the loot lying here |
| **R** | rest at the inn, or make camp |
| **F** | start the fight that is waiting |
| **M** | show or hide the region map |
| **J** | journal |
| **Esc** | close whatever is on top |

Clicking a node on the **region map** travels there directly, however many
stops away it is — the server routes the party and narrates each leg into the
log. A journey through dangerous country can be interrupted on the way.

In a conversation the number keys **1–9** pick a reply. In combat, click a
combatant to target them and choose an action from the bar.

## Architecture

```
/
  index.php, create.php, game.php, about.php
  sheet_print.php        the paper character sheet (see below)
  api/index.php          JSON API front controller
  app/
    bootstrap.php
    config/database.php
    lib/                 Dice, CharacterGenerator, LocationEngine, CombatEngine, …
  assets/css|js|images
  content/               the authored world: locations, npcs, dialog, quests, …
  sql/schema.sql, seed_data.sql, content.sql
  tools/                 load_content.py (the content importer), slice_assets.py
```

- **All content is data-driven** — the world graph, NPCs, monsters, items,
  quests and dialogue are JSON under `content/`, imported by
  `tools/load_content.py`. See `docs/CONTENT.md`.
- Browser talks only to PHP JSON endpoints (Fetch API).
- Combat state is stored in `combat_sessions.state_json` for future multiplayer locking.

### The world is a graph

A **region** is one map view; a **location** is a node on it — one described
scene with the people in it and named ways out. `location_exits` is the graph,
and travel is a server-side breadth-first search over it resolved hop by hop,
so a trip can be interrupted by what the party runs into. A character's whole
position is `characters.current_location_id`; there are no coordinates.

The region map is an inline SVG generated by `assets/js/ui-map.js` from the same
payload that draws the exit list — no image files, no library, nothing to bake.

### The printable character sheet

`sheet_print.php?character_id=N` renders one character in the standard 5e
layout — three columns, boxed abilities, all eighteen skills and six saves with
their proficiency marks, attacks, equipment, features — plus a second page of
spells for casters and no second page for anyone else. The **Print** button in
the in-game sheet header and **Print Sheet** on the character list both open it
with `&print=1`, which opens the browser's print dialogue on load.

There is no PDF library. The browser's own print pipeline is the renderer:
`assets/css/sheet-print.css` sets `@page { size: letter portrait }` and the
page is laid out in inches and points, so the on-screen preview is the same
size and shape as the paper. Adding a PHP PDF extension would mean changing
`docker/php/Dockerfile`, which is pinned to mirror what is enabled on hermes.

Every number comes from `app/lib/CharacterSheet.php`, which asks `Rules` for
all of it — the template does no arithmetic. Access is `Ownership::character()`
and nothing narrower: you may print any character of yours, including one from
a game you are not currently playing. `tools/test_ownership.sh` asserts that
one player cannot print another's.

Two things print as empty boxes on purpose: the death saves and the spell slots
that are currently spent. Both are true right now and false by the weekend, and
a sheet somebody carries around should not state a moment as if it were a fact.
Personality, ideals, bonds and flaws are blank because `characters` has no
column for them.

### The client

Plain `<script>` tags sharing globals — no modules, no bundler, no build step.
`game.php` loads them in order and each attaches exactly one global:

| File | Global | What it owns |
|------|--------|--------------|
| `api.js` | `API` | the fetch wrapper |
| `game.js` | `Game`, `RPGGame` | state, boot, the map renderer, walking about |
| `ui-panels.js` | `UI` | the two rails, the modal stack, journal, sheet, camp, shop |
| `ui-check.js` | `Check` | the d20 ceremony |
| `ui-dialog.js` | `Dialog` | the dialogue theatre |
| `ui-combat.js` | `Combat` | the four-column combat board |
| `editor.js` | — | the map editor, gated on `body.editing` |

Each file reaches for the others from **inside functions**, never at load time,
so load order beyond "game.js first" does not matter and dropping any one of
them leaves the rest able to say so rather than throwing on parse.

`window.RPGGame` stays exactly what it was: the editor's narrow, one-way bridge
into the renderer. `window.Game` is the wider seam the four screens are built
on. They are separate so that widening one cannot quietly widen the other.

The screen is three columns:

```
.game-shell
  .party-rail    132px   four compact cards: face, HP, AC, condition pips,
                         and for a companion how they feel about you
  .game-main             topbar / .map-frame / .action-bar
  .context-rail  150px   the tracked quest's current objective, then a
                         tabbed Log | Rolls | Map
```

`.map-frame` is what combat and the dialogue theatre are positioned against.
They cannot live inside `#map-area`, because that scrolls its own content and
anything absolutely positioned in it drifts away the moment the camera pans —
which is what used to happen to the quest banner.

`python3 tools/lint_js.py` runs `node --check` over every file, resolves every
API route the client asks for against the actions `api/index.php` actually
handles, and flags a `window.X` that nothing assigns. Same spirit as
`tools/lint_php.py`: it catches the mistake that costs the most to find by
hand, on the paths nobody plays.

### The d20 ceremony

The feature the two-phase check exists for. `check/request` (or a dialogue
choice carrying one) answers with the DC, the modifier broken into the pieces
that made it, the odds, and everything the party could spend; the player looks
at all of that and decides. Then `check/resolve` throws the die on the server
and the client animates onto `result.natural`.

> The die never decides anything. It cycles faces with a decreasing frequency
> and settles on the number that already came back, because a client that
> picked the number could be reloaded until it picked a better one — which is
> the whole reason `request` and `resolve` are two calls with nothing but an
> opaque token between them.

`successProbability()` in `ui-check.js` is a transcription of
`CheckService::successChance`, counted face by face for the same reason: a
natural 20 always succeeds and a natural 1 always fails whatever the DC, and no
closed form for "d20 + mod beats DC" agrees with that at either end of the die.
**The two must agree** — if they drift, the percentage visibly jumps the moment
the player toggles a boost, which reads as the game changing its mind. Toggling
a boost extends it rather than replacing it: the odds are averaged over the
boost's dice, and Halfling Lucky is folded in the way `resolvePending` applies
it, after the mode rather than as a flat bonus.

Advantage and disadvantage show both dice with the kept one unmistakable. A
natural 20 and a natural 1 get their own louder treatment, because
`CheckService::outcomeOf` makes them a critical and a fumble on any check and
that house rule is what the ceremony is selling. Under
`prefers-reduced-motion` the whole thing skips to the result.

### The location screen

The scene is type. `renderLocation()` in `assets/js/game.js` builds it in the
order a player thinks about it: where am I, what is it like, who is here, what
can I do, where can I go — then the chart, which is the same information as the
exits in a shape you can plan a journey on.

Three things are worth knowing about it:

**The measure is the design.** `.loc-inner` is capped at 62ch. Prose that runs
the width of a 2560px monitor is unreadable however good it is, and this is a
game made almost entirely of prose.

**People are a list, and that is the point of the pivot.** A market square holds
a dozen townsfolk; as sprites they were an unreadable pile, and as two lists —
the authored cast, then the crowd, muted — they are a menu. Somebody the party
has not met shows their *role* rather than their name ("Innkeeper", not "Mara
Hearthstone"), which is why talking to people is how you learn who they are.

**Portraits survive.** `<key>_face.png` in the people list and the party rail,
`<key>_bust.png` in conversation, and the full combat art on the cards. What
died with the tiles is the walk sheets, the terrain, the decor and the
buildings — still on disk under `assets/images/`, referenced by nothing.

### Travel

Clicking an exit, a chart node, or the tracker's next-step button all call
`Game.travelTo(locationId)` → `POST location/travel`. The server finds the path
(breadth-first over the exits the party can actually use — a locked or unfound
exit is not an edge), then walks it hop by hop, and each arrival may roll that
location's `random_encounter_pct` against its region's pool. A hit stops the
party where the fight found them and comes back `interrupted`.

The client narrates: each hop's authored label is logged in turn, paced so a
journey reads as one. That log is the transcript of the playthrough and is most
of what a text game gives a player to look back on.


### Combat

Fights are fought on a **sixteen-by-twelve grid of five-foot cells** — eighty
feet by sixty — generated per encounter and held in the session blob. Positioning
is a distance:

- **Movement is a budget of feet.** `speed` refills `move_left` at the start of
  each turn and walking spends it along a path the server finds. Terrain can
  cost double or refuse entry, hostile bodies block, friendly ones can be
  squeezed past but not stood on, and nobody cuts the corner between two walls.
- **Reach is a number.** A sword reaches one cell, a halberd two, a shortbow
  sixteen — and past its normal range it shoots at disadvantage. Spell ranges
  come from `spells.range_text`, which was prose on the card and is now the rule.
- **Obstacles give cover** — half (+2) or three-quarters (+5) to AC, and to
  Dexterity saves against an area effect. A wall gives *total* cover, which is
  not a bonus but the absence of a shot: `losClear()` decides it, so an
  unreachable target simply is not a target.
- **Leaving somebody's reach provokes an opportunity attack**, so Disengage is a
  real action rather than the logged apology it was for most of the game's life.
  Circling within reach provokes nothing.
- **Flanking** — an ally directly opposite the target — gives advantage. So does
  Pack Tactics, which is now literally the SRD's "an ally within 5 feet". They do
  not stack, because advantage never does.
- **Shooting with an enemy at your elbow** is disadvantage.

Distance is **Chebyshev** — every square is five feet, including diagonals, which
is the SRD default. The 5-10-5 variant was rejected deliberately: under it the
cost of reaching a cell depends on the path taken, so the reachable set stops
being a search over static edge weights and straight-line range stops agreeing
with movement cost. The visible symptom would be a board offering a move the
server then refuses.

**The old rank survives, demoted.** `characters.combat_rank`, `monsters.rank_pref`
and `encounter_monsters.rank_override` are all still read, and they decide one
thing: which end of your deployment zone you start in. No rule consults `rank`
after `BattleMapGen::deploy()` has run.

Terrain is generated by `BattleMapGen`, seeded from the encounter and the place —
so an authored fight always looks the same and the boulder is where you left it.
The palette comes from the location's `location_type` and its region's
`region_type`: tables and a hearth in a town building, stalagmites and pits in a
dungeon room, trees and a stream in the wilderness. Nothing is ever stamped
inside a deployment zone, which is most of the guarantee that nobody spawns
walled in; the rest is a flood fill that carves a road if one is missing.

> The fighting pit passes its own map seed. `PitEngine::bout()` rewrites one
> scratch encounter row per party, so deriving the seed from that row's id would
> put every bout a player ever fights on one identical battlefield.

`app/lib/BattleGrid.php` holds all of it — distance, sight, cover, pathfinding,
threatened cells, flanking, templates — as pure statics over a terrain array. No
PDO, no session, no knowledge of what a spell is. That is what lets
`tools/test_combat.php` settle an argument about a cone without starting a fight.

Everything that touches dice goes through the rules layer rather than being
approximated in the engine: attack rolls take advantage from
`Conditions::attackContext()`, criticals double the dice and not the modifier
(`Dice::rollDetailed($expr, true)`), damage runs through
`Rules::damageAfterDefenses()` so a Skeleton's bludgeoning vulnerability applies,
and a spell with `resolution = 'save'` makes its **target** roll against
`Rules::spellSaveDc()`. Slots are read from `characters.spell_slots_json` against
`Rules::slotTable()` and written back the moment they are spent.

A player character at 0 HP is **Unconscious, not dead** — the condition goes on
and `alive` stays true, so a heal has something to bring back. Monsters at 0 are
dead. The fight is lost when the last conscious party member falls.

#### What the board draws

`ui-combat.js` draws **four columns**: the initiative ribbon from `state['order']`
along the top, your party's cards on the left, the enemy's on the right, the
battlefield across the middle two, and an action bar underneath carrying the
action economy, the feet of movement left and the caster's remaining slots. The
target inspector floats over the map rather than taking a column of its own.

The ribbon is worth calling out: the old screen iterated `combatants` and so
never showed turn order at all, even though `order` had been in the state the
whole time. Turn order is the one thing a turn-based fight is unplayable
without.

`ui-battlemap.js` draws the board as inline SVG on a `0 0 16 12` viewBox — one
cell is one unit, so the combatant at (3,7) is drawn at `translate(3.5 7.5)` and
there is no conversion to get wrong. It follows `ui-map.js`'s conventions
throughout: a fixed unit viewBox, a `<g transform>` per token, invisible hit
shapes so the click target is a finger rather than a glyph, and
`role="button" tabindex="0"` with its own keydown handler because an SVG group
takes focus but does not fire a click on Enter. It deliberately has **no zoom or
pan** — a whole battlefield is sixteen cells across and fits legibly in its
column, so ui-map's 175-line pointer state machine buys nothing here.

**The client does no geometry.** Three rules used to be mirrored in JavaScript —
`legalTargets`, the rank capacity, which rank was the other one — each carrying a
comment conceding that a copy of a server rule drifts. They are gone. The engine
sends a derived `state['ui']` after every action:

```
'ui' => ['actor'   => cid,
         'reach'   => ['5,7' => ['cost'=>10, 'from'=>'4,7', 'end'=>true, 'provokes'=>0], …],
         'threat'  => ['6,7' => [cid, …], …],
         'targets' => [cid => ['dist'=>25,'cover'=>2,'long'=>false,'mode'=>'normal','why'=>''], …]]
```

`reach` carries the **predecessor** the pathfinder already recorded, so hovering
a cell draws the exact route the server would take — no request, and no second
pathfinder to disagree with the first. Mirroring a pathfinder would have been the
`legalTargets` mistake at ten times the size, and its failure mode is the worst
kind: a board that offers a move the server then refuses.

Note that `ui` is derived and non-authoritative — nothing on the server reads it
back — and that an empty PHP array encodes as `[]` rather than `{}`, which
round-trips through the blob, so both shapes genuinely arrive at the client.

The cards themselves are **unchanged** from the rank board: same width, same
`data-cid`, same three visual channels (border is reachability, outline is
selection, the `::before` ring is whose turn). That is why `playClip()`,
`flash()`, `float()` and `stepHp()` needed no changes at all — they resolve
`.cbt-card[data-cid]` and it is still there. Tokens get their own CSS-only
feedback, with the same one-channel-per-fact discipline; the one technique that
does not port is the pseudo-element turn ring, because SVG has no `::before`.

The dead stay on the board, greyed and unclickable, until the next action:
seeing what you killed is most of how a fight reads, and the death clip needs
something to play over.

#### `state['events']`

Alongside `state['log']`, which is what the player reads, the engine emits
`state['events']`: a machine-readable list of what the last action did, cleared
at the start of every action. The client animates from that.

```
['type'=>'attack','actor'=>cid,'target'=>cid,'hit'=>true,'crit'=>false,
 'natural'=>17,'total'=>21,'ac'=>15,'damage'=>8,'damage_type'=>'slashing',
 'cover'=>2,'dist'=>25,'long'=>false]
['type'=>'save','actor'=>cid,'ability'=>'dex','dc'=>13,'natural'=>9,'total'=>11,'passed'=>false]
['type'=>'condition','target'=>cid,'key'=>'frightened','applied'=>true]
['type'=>'move','actor'=>cid,'from'=>[3,5],'to'=>[7,5],'path'=>[[3,5],…],'cost'=>20]
['type'=>'opportunity','actor'=>reactor,'target'=>mover,'at'=>[3,5]]
['type'=>'aoe','actor'=>cid,'spell'=>'Burning Hands','shape'=>'cone','ft'=>15,
 'origin'=>[3,5],'toward'=>[7,5],'cells'=>['4,5',…]]
['type'=>'death','target'=>cid,'dead'=>false]   ['type'=>'heal',…]
['type'=>'cast',…]  ['type'=>'concentration_broken','actor'=>cid,'spell'=>'Bless']
```

`opportunity` is emitted **before** the `attack` it causes, so the reaction reads
as a reaction. `aoe` is emitted before the per-target saves, so the footprint is
painted before anything lands inside it. There is deliberately no `cover` event:
cover is a modifier on an attack rather than a thing that happens, so it rides on
the `attack` event as a field — an event type per modifier would be a new event
for every rule. `['type'=>'rank',…]` is retired with the ranks.

The client used to pick the English log apart with regexes to decide what to
animate, which meant rewording a log line silently killed an animation. Events
exist so that cannot happen again: the log is prose and may be reworded freely.

#### Monster AI

A pathfinder feeding a utility scorer. `runMonsterAI()` enumerates three kinds of
option — shoot from here, walk somewhere and then attack, or just walk somewhere
better — scores each with `CombatEngine::scoreOption()` and takes the best:
finish the wounded, kill the artillery (casters and healers) before the brute,
prefer soft AC, take Pack Tactics and flanking where they are free, prefer the
clean shot to the one through cover, break off when badly hurt *and* able to
shoot from out of reach, and close on whoever is worth reaching otherwise. The
weights are a block of named constants at the top of the class.

**`scoreOption()` is pure and must stay pure** — not one `BattleGrid` call
belongs in it. Every spatial fact an option depends on (how many opportunity
attacks the walk costs, how much cover the destination gives, how many enemies
threaten it) is counted by `runMonsterAI()` and handed in as a plain number.
That division is what lets `tools/test_combat.php` check the monster's judgement
against invented options with no board underneath them, and it is why the AI's
tuning survived the move from ranks to a grid intact.

For melee, only the eight cells around the target are considered as approach
positions rather than the hundred-odd a monster can usually reach. That is not an
optimisation to add later: six monsters all resolve inside one HTTP request.

Every rule in `BattleGrid`, `BattleMapGen` and the static half of `CombatEngine`
takes no PDO, so `php src/tools/test_combat.php` exercises them with no database
— including a sweep of two hundred seeds per palette asserting every generated
map is playable, and a line-of-sight symmetry sweep. `bash
src/tools/test_grid_combat.sh` covers the other half over real HTTP: that a fight
starts on a real battlefield, that walking works and illegal walks are refused,
that the AI cannot deadlock on a map it has to cross, and that a session written
by the rank engine is retired rather than resumed.

### Regenerating art from the RPG Maker packs

Tiles, scenery and sprites are cut from the PVGames *Medieval* packs by
`tools/slice_assets.py`. Edit a manifest at the top of that file
(`GROUND`, `PROPS`, `DECOR`, `ANIMATED`, `BUILDINGS`, `CLASS_SPRITES`, `NPCS`,
`MONSTERS`, `BATTLERS`, `MVSV`), then:

```bash
python3 tools/slice_assets.py --preview preview.png
```

`--preview` writes a contact sheet of everything it cut — the quickest way to
check a new pick. To find pieces on an object sheet, index it first:

```bash
python3 tools/slice_assets.py --catalog "Medieval T&C/Medieval_T&C_Tiles/Town_1.png"
```

That finds each loose prop by its alpha outline and writes a numbered contact
sheet; `DECOR` refers to pieces by those numbers.

#### Animated scenery

The packs ship 34 "Animated Pieces" sheets — fire, torches, braziers, candles,
chandeliers, magic orbs, smoke. They are RPG Maker `$` character sheets: one
object as **3 animation columns × 4 variant rows**, cell = width/3 by height/4,
with unused variant rows left blank.

`ANIMATED` in `tools/slice_assets.py` cuts one row into a horizontal strip of 3
frames under `assets/images/anim/`, alongside an `index.json` recording each
strip's frame count and frame size. The renderer has to clip to exactly one
frame and a strip cannot say how wide that is, so the slicer records it at cut
time.

> Frames are cropped to the **union** of all three bounding boxes, never trimmed
> individually. Trimmed separately they would each have their own size and
> offset, and a flame animated that way lurches around its own base instead of
> flickering in place.

**Whether a piece animates is a property of the artwork, not of the placement.**
Anything under `anim/` animates; `map_decor` gains no columns, so there is no
per-placement copy of the frame data to drift out of step with the file.
`MapEngine::animFor()` attaches `frames` / `frame_w` / `frame_h` to decor rows
at read time.

Playback is a one-frame window with the strip slid through it:
`translateX(0 → -100%)` under `steps(N)`. That combination is exact — -100% of
the strip is N frame widths and `steps(N)` samples it at k/N, landing on -k
frames precisely. Animating a percentage `background-position` instead lands on
the wrong offsets, the same trap the walk sheets hit. Animation is disabled
under `prefers-reduced-motion`.

#### Portraits, battlers and combat clips

Every actor folder carries more than a walk cycle, and four more categories are
cut from it:

| Output | From | Notes |
|--------|------|-------|
| `monsters/<key>_face.png`, `_bust.png` | `_Face.png`, `_Bust.png` | monsters get portraits on the same terms as NPCs |
| `battlers/<key>.png` | `_Battler.png` | 1024px front-facing battle art, trimmed and scaled to `BATTLER_PX` |
| `npcs/<key>_bust_2.png` … | `_Bust_2` … `_Bust_8` | expression sets, counted in `busts.json` |
| `combat/<key>_<clip>.png` | `_MVsv_alt_<clip>.png` | 3-frame side-view poses, indexed in `index.json` |

The Heroes pack draws each face eight times over — neutral, angry, pleased and
so on — while townfolk and monsters ship one. Expression 1 keeps the plain
`<key>_bust.png` name it has always had, so nothing that already points at it
has to change. `busts.json` in `npcs/` and `monsters/` records `{"<key>": N}`,
for the same reason `anim/index.json` exists: nothing can count expressions by
looking at one file, and `npcs.bust_count` is loaded from it.

`MVSV` lists which of the ~34 side-view poses to cut — currently `attack1`,
`magic`, `shooting`, `dead1`, `victory1`, `stance1`, enough to narrate a round.
`combat/index.json` uses the **same schema** as `anim/index.json`, so the
renderer clips these strips with the existing code path. Frame width is read off
each sheet rather than assumed: the poses are 128px for a goblin but 192 for an
ogre and 256 for a golem. As with animated scenery, the three frames are cropped
to their **union** — trimmed individually, a sword swing moves the fighter
instead of the sword.

Not every actor is drawn doing everything, and the script reports what it could
not find. The beasts (`wolf`, `stirge`, `giant_rat`) have no side-view art at
all, the four Interiors premades have no `shooting`, the wolf has no bust, and
`bandit` — a Townfolk sprite — has no battler. Those are gaps in the packs, not
failures of the slicer.

> The Timber Wolf disagrees with itself about its own name: its animation sheets
> say `Medieval_TC_TimberWolf` while its face and battler say
> `Medieval_T&C_TimberWolf`. `actor_file()` falls back to matching the suffix
> alone, since a folder holds one actor.

#### Coverage of the Interiors pack

`Medieval Interiors` ships fourteen object sheets. `DECOR` now draws on nine of
them — `ItemClusters`, `Furniture_1`, `Furniture_2`, `Tavern`, `Shop`, `Church`,
`Profession_1`, plus `A4`/`A5` for floors. Notably `ItemClusters` holds whole
arrangements rather than single objects: tables already laid with plates and
food, benches included, which is what indoor scenes actually need.

Still unmined, if more variety is wanted later:

| Sheet | Loose pieces | Contents |
|-------|--------------|----------|
| `Profession_2` | 103 | smithing, milling, more trade tools |
| `Shop_2` | 62 | further merchant fittings |
| `Regal` | 48 | noble/castle furnishings |
| `Walls_1`, `Walls_2` | — | wall autotiles, not loose scenery |

Add them by cataloguing the sheet and appending to `DECOR`; nothing else needs
to change, because the map editor lists whatever is on disk.

The packs are licensed art: usable in this project, but **not** redistributable.
They therefore live **outside the web root**, at `/home/www/rpg-assets-src` —
a sibling of this directory, so nginx (whose root is `/home/www/rpg`) never
serves them. Only the sliced output under `assets/images/` is public. Override
the location with `RPG_PACK_DIR`:

```bash
RPG_PACK_DIR=/path/to/packs python3 tools/slice_assets.py
```

The generators are the only thing that reads the packs, so the game runs fine
without them present — you just can't re-cut art until they're restored.
